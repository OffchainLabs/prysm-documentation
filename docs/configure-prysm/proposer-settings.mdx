**Proposer settings** control how your validator client proposes blocks: for each validator key, the fee recipient, gas limit, graffiti, and builder configuration, plus a default for every key you don't configure individually. This page is the reference for the **version 2 (v2) schema**, introduced for the [Gloas](https://eips.ethereum.org/EIPS/eip-7732) fork.

Before Gloas, the `builder` section only said whether to register a key with MEV-Boost relays. From the fork, builders are on-chain participants that your validator asks for bids directly, so v2 adds fields for which builders to use, how much of their promised payment to count, a minimum bid, and how to weigh bids against your own block, and it moves the gas limit out of `builder`.

If you only need to set a fee recipient, see [Configure Fee Recipient](/configure-prysm/configure-fee-recipient.mdx). For how builders work before and after Gloas, see [Configure MEV Builder](/configure-prysm/configure-mev-builder.mdx).

:::tip Already using MEV-Boost? Migrate before the fork

v1 builder settings (`enabled` and the `gas_limit` inside `builder`) stop working at the Gloas fork, and Prysm doesn't convert them. Most operators need one change before then: replace `enabled` with a `builders` list. It is safe to do now. See [Migrating from v1 to v2](#migrating-from-v1-to-v2).

:::

<span id="requires-gloas"></span>

:::info Requires the Gloas fork

The builder fields, the `--builder-*` flags, and the keymanager `builder_config` endpoints on this page only work on networks with a Gloas fork epoch scheduled: testnets and devnets first, and mainnet once the fork is scheduled there. On other networks, a v2 file still loads, but bids are never requested, and the endpoints return `501`. Fee recipient, gas limit, and graffiti settings work everywhere. Until the fork epoch, builders still run through MEV-Boost, and a `builders` list only decides which keys register; see [Running v2 settings before the Gloas fork](#running-v2-settings-before-the-gloas-fork).

:::

In a file, `default_config` is the settings for every key that has no entry of its own under `proposer_config`, so here it covers every key; the flags set the same defaults. The **Per key** tab shows the remaining fields.

**`max_execution_payment` is a trust decision.** A bid's `value` is guaranteed by the builder's staked balance; its `execution_payment` is only a promise to pay inside the block, which the protocol doesn't check. This field sets how much of that promise Prysm counts when it values the bid. The maximum, `18446744073709551615` (2^64 − 1), counts it in full, the same trust you gave a relay under MEV-Boost: a builder that doesn't pay can cost you the whole promised amount. A smaller value in gwei (`100000000` is 0.1 ETH) caps that loss. Unset or `0` counts nothing, so bids that depend on promised payment rarely beat your own block, and Prysm warns at startup about entries that leave it unset. Prysm has no separate flag gating this; the value itself is the opt-in. Set it per builder entry, or on the `builder` object as the default for all of its entries; the keymanager API reads and writes it per entry.

The listed key requests bids from two builders. Its `builder` object sets the defaults for both entries: ignore bids worth less than 0.01 ETH (`min_bid`), compare bids with the local block at face value (`builder_boost_factor: 100`), and count up to 0.1 ETH of promised execution payment (`max_execution_payment`). Builder A overrides that cap to count promised payments in full, accepts bids only from one builder public key (`builder_pubkeys`), and gets custom `auth_data` in the signed requests; builder B keeps the cap but raises its minimum bid to 0.02 ETH and has its bids counted at 90% of their value (`builder_boost_factor: 90`), which favors your own block. The key also pins its gas limit and graffiti; leave `gas_limit` out unless you want a fixed value (see the warning below). Every other key follows `default_config`, which requests no bids because its `builders` list is empty.

Builders are used only where a `builders` list says so: on the key itself, or in `default_config` for keys that don't set one. A key with no `builder` object follows `default_config` like any other field it leaves unset, so when the default lists builders, a key that should use none needs `"builders": []` of its own. See the [field reference](#field-reference) and [Inheritance and merge rules](#inheritance-and-merge-rules).

<span id="gas-limit-override"></span>

:::warning A gas limit you set overrides the gas limit schedule

From the Gloas fork onward, a `gas_limit` in your settings, per key or in `default_config`, or one passed with `--suggested-gas-limit`, is the gas limit your validator signs into its proposer preferences. It overrides the network's [scheduled gas limit](#the-gas-limit-schedule), so the key keeps that value and doesn't pick up scheduled increases. Prysm warns at startup when the flag is set, and once per epoch when it signs a preference that differs from the schedule. Unless you want a fixed gas limit, leave `gas_limit` unset and don't use the flag.

:::

### Configuring Gloas builders with flags

The flags set the same builder configuration for every key, the way `--suggested-fee-recipient` sets a default fee recipient. Per-key settings from a file, URL, or the keymanager API take priority over them.

| Flag | Effect |
|---|---|
| `--builder-urls` | Comma-separated builder URLs to request bids from, at most 64. Auth data agreed with a builder goes in a `0x`-hex fragment (`https://builder.example#0x0123`); otherwise the lowercased hostname is used. An invalid URL, a non-hex fragment, more than 64 entries, or a duplicate stops the validator client from starting. |
| `--builder-min-bid` | Minimum bid, in gwei: the bid value plus its execution payment, counted up to `--builder-max-execution-payment`. |
| `--builder-boost-factor` | Percentage applied to a bid's value before comparing it with your local payload: `100` is neutral, below `100` favors your payload, `0` always uses it (also against [P2P bids](#how-a-bid-is-valued)). |
| `--builder-max-execution-payment` | Maximum execution payment, in gwei, counted toward a bid: `0` counts only the value backed by the builder's stake, `18446744073709551615` counts promised payment in full. See [Configuring builders](#configuring-builders). |

Set `--builder-max-execution-payment` with `--builder-urls`; on its own, `--builder-urls` counts none of a builder's promised payment. Pass the flags on every start: they apply only to the run that sets them, and Prysm warns when it drops stored values because the flags are missing. Before the fork, a non-empty `--builder-urls` also registers keys with MEV-Boost, as `--enable-builder` does, including keys whose `builder` object has only v1 fields; set `"builders": []` on a key to keep it out.

## Migrating from v1 to v2

The v1 builder fields control MEV-Boost registration, which doesn't exist after the fork, so Prysm doesn't convert them; you replace them.

### What replaces what

| To set | v1 | v2 |
|---|---|---|
| The file's schema version | no `version` field, or `version: 1` | `version: 2`. Optional: a file with no `version` is treated as v2 once it has any v2 builder field below. If the file says `version: 1`, change it to `2` |
| Use builders for a key | `builder.enabled: true` | a non-empty `builder.builders` list |
| Use builders for every key, by flag | `--enable-builder` (registers every key; does nothing after the fork, and warns next to v2 settings) | `--builder-urls` with `--builder-max-execution-payment`, or a `builders` list in `default_config` |
| Don't request builder bids for a key | `builder.enabled: false` | `builder.builders: []`, or no `builder` object to follow `default_config` |
| Which builders to use | not possible: `--http-mev-relay` set one relay for every key | `builders[].url`, per key |
| Accept bids only from specific builders | not possible | `builders[].builder_pubkeys` |
| Authenticate your requests to a builder | not possible | `builders[].auth_data` (defaults to the URL's hostname) |
| A gas limit | `builder.gas_limit`, or `--suggested-gas-limit` | `gas_limit` next to `fee_recipient`, or `--suggested-gas-limit`; both override the [gas limit schedule](#the-gas-limit-schedule) from the fork onward, so leave them out to follow it |
| Ignore bids below a minimum | beacon node `--min-builder-bid`, for every key | `min_bid`, per builder config or per entry |
| Favor your local block over builder bids | beacon node `--local-block-value-boost`, for every key | `builder_boost_factor`, per builder config or per entry |
| Count a builder's promised execution payment | not possible: you relied on the relay | `max_execution_payment`, per builder config or per entry; unset counts none |
| Relays | `relays` | deprecated and ignored, because Gloas has no relays |
| Generate the builder fields with `prysmctl validator proposer-settings` | `--with-builder` | not available: the flag still writes v1 fields and warns, so add the `builders` list by hand |
| A fee recipient or graffiti | `fee_recipient`, `graffiti` | unchanged |

### How to migrate

1. Replace each `"enabled": true` with a `builders` list and set `max_execution_payment` on each entry. Replace each `"enabled": false` with `"builders": []`, or remove the `builder` object if the key should follow `default_config`.
2. **Delete `gas_limit` instead of moving it**, unless you want a fixed gas limit. Next to `fee_recipient`, it overrides the [gas limit schedule](#the-gas-limit-schedule) from the fork onward; inside `builder` it never did. Remove `--suggested-gas-limit` for the same reason.
3. Delete `relays` if present. Optionally add `"version": 2`; the builder fields already make the file v2.
4. Restart the validator client and check the [startup logs](#startup-warnings-explained). The beacon node keeps using `--http-mev-relay` until the fork; after the fork epoch, remove it and `--enable-builder`, and stop MEV-Boost.

### Running v2 settings before the Gloas fork

You can migrate at any time before the fork. Until the fork epoch, your validator still uses MEV-Boost, and your v2 settings decide which keys to register:

| Your v2 settings | Before the fork (MEV-Boost) | After the fork (Gloas) |
|---|---|---|
| Non-empty `builders` list | Key is registered with MEV-Boost relays, as with v1 `enabled: true` | Bids are requested from the listed builders |
| Empty list (`builders: []`) | Key is **not** registered, unless the legacy `enabled: true` is also set | No builder bids are requested |
| No `builders` field, but other builder fields set (`min_bid`, etc.) | The key's own config doesn't decide; the `default_config` setting applies, if any | Uses the `builders` list from `default_config` |
| Legacy `enabled: true` together with v2 fields | Key is registered | `enabled` is ignored, and removed at the fork |

Registration still uses your fee recipient and gas limit (a `gas_limit` next to `fee_recipient` wins over a legacy one inside `builder`), and the beacon node's `--http-mev-relay` setup doesn't change until the fork. The keymanager `builder_config` endpoints return `501` until your network schedules the fork.

### What happens if you don't migrate

Nothing changes before the fork, except that Prysm warns at startup about deprecated v1 builder fields once your network schedules Gloas. At the fork epoch, Prysm removes `enabled` and the `gas_limit` inside `builder` with a warning and keeps fee recipients and graffiti. Your gas limit follows the network schedule, and Prysm requests no builder bids until you add v2 settings (trustless P2P bids can still beat your own block; see [How a bid is valued](#how-a-bid-is-valued)). Nothing in this fallback counts as a payment that isn't backed by a builder's staked balance.

## How proposer settings are supplied

- **Command-line flags**, which set `default_config` for every key: `--suggested-fee-recipient`, `--suggested-gas-limit`, and the [builder flags](#configuring-gloas-builders-with-flags).
- `--proposer-settings-file=<path>`: a local JSON or YAML file using the schema on this page.
- `--proposer-settings-url=<url>`: a URL that returns the same schema as JSON (Prysm sends a GET request; YAML is only supported for files).
- [Keymanager APIs](/apis/keymanager-api.mdx): endpoints for each key's fee recipient, gas limit, graffiti, and builder configuration.

`--proposer-settings-file` and `--proposer-settings-url` can't be combined; the validator client won't start with both. Files and URL responses are parsed strictly: a field name Prysm doesn't recognize, a `version` above `2`, or a `builder_pubkeys` or `auth_data` value that isn't `0x`-hex stops the settings from loading. (`pubkeys`, the old name of `builder_pubkeys`, is the common case.)

A `default_config` in a file or URL replaces the defaults set by flags, including `--suggested-fee-recipient` and `--suggested-gas-limit`, so put those values in the file. With a v1 file, `--suggested-gas-limit` also overwrites the `gas_limit` inside `builder` for every key, as it always has.

The validator client saves loaded settings to its database, so changes made through the keymanager APIs survive restarts. A file or URL takes priority over the database at startup: a non-empty `proposer_config` replaces all stored per-key settings, and a `default_config` replaces the stored default. If you manage keys through the keymanager APIs and restart with a settings file, those keys are reset to what the file says.

## Field reference

Amounts and gas limits can be written as strings (`"60000000"`) or plain numbers; strings are recommended because the keymanager API uses them. `version` must be a plain number. All amounts (`min_bid`, `max_execution_payment`) are in gwei.

### Top-level fields

| Field | Description |
|---|---|
| `version` | **Optional.** `2` is the current schema. A file with no `version` is treated as version 2 as soon as it contains any v2 builder field (`builders`, `min_bid`, `builder_boost_factor`, or `max_execution_payment`), with an info log. Don't set `version: 1` on a file with v2 builder fields; Prysm takes the version as written. A `version` above `2` fails to load. |
| `proposer_config` | A map from validator BLS public key (98-character `0x`-prefixed hex) to the options for that key. |
| `default_config` | Options for every validator key not listed in `proposer_config`. |

### Options (per key, and in `default_config`)

| Field | Description |
|---|---|
| `fee_recipient` | The Ethereum address that receives priority fees and, after Gloas, builder payments. A per-key value overrides `default_config`, which overrides `--suggested-fee-recipient`. |
| `gas_limit` | The gas limit your validator asks for in blocks built for it. **New in v2 at this level.** Leave it unset to follow the network's [scheduled gas limit](#the-gas-limit-schedule), or the chain default in your Prysm release when no schedule entry applies (the [command-line options](/configure-prysm/command-line-options.mdx) page shows that default for `--suggested-gas-limit`). Set it only to use a fixed value instead; see [the warning above](#gas-limit-override). In v1, the gas limit was set inside `builder`; that location stops working at the Gloas fork. |
| `graffiti` | The graffiti string included in blocks proposed by this key. |
| `builder` | Builder configuration for this key. See below. Leave it out to use the builder configuration from `default_config`. |

### The `builder` object

| Field | Description |
|---|---|
| `builders` | The builders this key requests bids from. See [Builder entries](#builder-entries). Leaving it out means the key uses the list from `default_config`; an empty list (`[]`) means it requests bids from no builders (bids broadcast over P2P can still win; see [How a bid is valued](#how-a-bid-is-valued)). At most 64 entries. Duplicate or invalid entries are dropped with a warning; values that aren't valid `0x`-hex fail the load. |
| `min_bid` | Minimum [effective value](#how-a-bid-is-valued), in gwei; lower bids are ignored. Unset means no minimum. Can be overridden per entry. |
| `max_execution_payment` | Maximum execution payment, in gwei, counted toward a bid: unset or `0` counts none, `18446744073709551615` counts it in full. This is how much you trust the builder to pay; see [Configuring builders](#configuring-builders). Can be overridden per entry. |
| `builder_boost_factor` | Percentage applied to bid values before comparing them with your local block: `100` (default) is neutral, above favors builders, below favors your block, `0` means a bid never wins. Can be overridden per entry. |
| `enabled` | **Legacy (v1).** Registers the key with MEV-Boost before the Gloas fork, even next to `builders: []`. Ignored by the Gloas builder settings and removed at the fork. In v2, a non-empty `builders` list registers the key instead; see [Running v2 settings before the Gloas fork](#running-v2-settings-before-the-gloas-fork). |
| `gas_limit` | **Legacy (v1).** The MEV-Boost registration gas limit. In v2, set `gas_limit` next to `fee_recipient` instead. |

The v1 `relays` field is deprecated and ignored, but still accepted.

### Builder entries

Each entry in a `builders` list describes one builder your validator can request bids from:

| Field | Description |
|---|---|
| `url` | **Required.** The builder's HTTP(S) endpoint, up to 2048 bytes, with an ASCII hostname. Entries with the same `url` and `auth_data` are duplicates. |
| `min_bid` | Overrides the enclosing config's `min_bid` for this builder. |
| `max_execution_payment` | Overrides the enclosing config's `max_execution_payment` for this builder. |
| `builder_boost_factor` | Overrides the enclosing config's `builder_boost_factor` for this builder. |
| `builder_pubkeys` | Optional allowlist of builder BLS public keys (48-byte `0x`-hex strings, at most 64). If set, only bids from these builders are accepted from this URL. |
| `auth_data` | Optional bytes, as a `0x`-hex string, that your validator signs to authenticate its requests to this builder. Defaults to the lowercased hostname of `url` (`builder.example`; IPv6 in brackets), as the [builder spec](https://github.com/ethereum/builder-specs/blob/main/specs/gloas/validator.md#default-auth-data) defines, so most operators never set it. At most 4096 bytes. |

A field not set on an entry is taken from the enclosing `builder` config, and then from the `builder` config in `default_config`. `builder_pubkeys` and `auth_data` use the same names and `0x`-hex format as the [keymanager builder API](#keymanager-apis), you can copy an entry between the two. Files written for an earlier development build used a `pubkeys` field with base64 values; rename the field and convert each value to hex (`echo '<base64 value>' | base64 -d | od -An -tx1 | tr -d ' \n'`, then prefix `0x`).

## How a bid is valued

After Gloas, the beacon node builds a local payload for every proposal, requests bids from your configured builders (in parallel, with a `600ms` budget by default; `--builder-bid-timeout` on the beacon node), and collects bids broadcast over the P2P network. Each bid that passes the chain's validity checks is valued at its `value`, which the protocol guarantees from the builder's staked balance, plus its `execution_payment`, which the builder only promises to pay, counted up to your `max_execution_payment`. Bids below `min_bid` are discarded; the rest are multiplied by `builder_boost_factor / 100`, and the highest is compared with your local payload. Ties go to your own block.

**Bids from the P2P network.** Builders can also broadcast bids to every proposer over P2P without any configuration. These must carry a zero `execution_payment`, so only their guaranteed `value` counts, and Prysm compares them with your local payload on every proposal, whether or not you configured any builders, using the `min_bid` and `builder_boost_factor` from your builder config (none and `100` if you have no config). An empty `builders` list stops bid requests, not P2P bids; to always use your own block, set `builder_boost_factor` to `0`.

If no bid wins, your validator uses its own payload. A builder that wins and then doesn't reveal its payload is blacklisted for the rest of the epoch, or for 256 epochs after a second failure within five, and its bids are ignored meanwhile; see [How a Gloas proposal uses builders](/configure-prysm/configure-mev-builder.mdx#how-a-gloas-proposal-uses-builders) for the full flow.

## The gas limit schedule

From the Gloas fork, a key with no `gas_limit` of its own indicates the network's scheduled gas limit ([EIP-8261](https://eips.ethereum.org/EIPS/eip-8261)), taken from the `GAS_LIMIT_SCHEDULE` entries in the network config, or the chain default when no entry applies yet. Prysm ships the schedule for the networks it supports. On a custom network or devnet, pass the network's `config.yaml` to the validator client with `--chain-config-file` too, or it won't have one. To see the gas limit a key signs, call the keymanager `GET /eth/v1/validator/{pubkey}/gas_limit` endpoint.

## Inheritance and merge rules

`min_bid`, `max_execution_payment`, and `builder_boost_factor` are inherited one field at a time. A per-key value takes priority. If the key doesn't set a field, the value from `default_config` is used. If neither sets it, the default applies: no minimum bid, no promised payment counted, and a boost factor of 100. Builder entries inherit from their enclosing config in the same way.

The `builders` list is **replaced, not merged**. A per-key list, including an empty list (`[]`), replaces the default list completely. If a key doesn't set `builders`, it uses the default list, and a key with no `builder` object at all uses the whole `builder` object from `default_config`. So to stop a single key from requesting builder bids, set `"builders": []`.

`gas_limit` works the same way: a per-key value takes priority over `default_config`. If neither sets it, the network's scheduled gas limit or the chain default applies.

## Keymanager APIs

The fee recipient, gas limit, graffiti, and `builder_config` endpoints read and write these settings for one key at a time; see [Keymanager APIs](/apis/keymanager-api.mdx#proposer-settings-endpoints) for their behavior and wire format. Changes made through them survive restarts unless a settings file or URL replaces them at startup, as described in [How proposer settings are supplied](#how-proposer-settings-are-supplied).

## Startup warnings explained

Unknown fields, a `version` above `2`, invalid builder flags, and `builder_pubkeys` or `auth_data` values that aren't `0x`-hex stop the settings from loading. Builder entries that break a size or format limit are dropped with a warning instead. Most messages below appear at startup; a few repeat as long as the cause remains.

## Frequently asked questions

#### Do I have to do anything if I never use builders?

Set your fee recipient, with a flag or in a file. You don't need `"version": 2`, a `builder` section, or any new flags. After the fork, your validator requests no builder bids and its gas limit follows the network schedule, unless you set `--suggested-gas-limit` or a `gas_limit`. Trustless bids broadcast over P2P can still beat your own block; see [How a bid is valued](#how-a-bid-is-valued) if you never want that.

#### Can I mix the flags and a v2 file?

Yes, and the file takes priority: a `default_config` in the file replaces all flag defaults, so put your fee recipient and any gas limit in the file rather than in `--suggested-fee-recipient` or `--suggested-gas-limit`. `--enable-builder` only affects registration before the fork; `--suggested-gas-limit` keeps applying after it and overrides the schedule. Prysm warns about both.
