**Proposer settings** control how your validator client proposes blocks: for each validator key, the fee recipient, gas limit, graffiti, and builder configuration, plus a default for every key you don't configure individually. This page is the reference for the **version 2 (v2) schema**, introduced for the [Gloas](https://eips.ethereum.org/EIPS/eip-7732) fork.

Before Gloas, the `builder` section only said whether to register a key with MEV-Boost relays. From the fork, builders are on-chain participants that your validator asks for bids directly, so v2 adds fields for which builders to use, how much of their promised payment to count, a minimum bid, and how to weigh bids against your own block, and it moves the gas limit out of `builder`. If your settings file configures builders, update it before the fork: v1 builder settings keep working until then, and at the fork Prysm removes them and uses defaults. See [Migrating from v1 to v2](#migrating-from-v1-to-v2).

If you only need to set a fee recipient, see [Configure Fee Recipient](/configure-prysm/configure-fee-recipient.mdx). For how builders work before and after Gloas, see [Configure MEV Builder](/configure-prysm/configure-mev-builder.mdx).

## Using one builder for all keys

The simplest setup gives every key the same builder URL and a `max_execution_payment` for it:

**Set `max_execution_payment` with the URL.** A builder's bid can pay you in two ways: `value`, which the protocol takes from the builder's staked balance, and `execution_payment`, which the builder only promises to pay inside the block. If `max_execution_payment` is unset, it is `0` and Prysm counts only `value`, so a builder that pays mainly through `execution_payment` almost never beats your local block. On networks with Gloas scheduled, Prysm warns at startup about entries that leave it unset (an explicit `0` is taken as deliberate).

**The value is in gwei** (1 ETH = 1,000,000,000 gwei), so `100000000` is 0.1 ETH:

| ETH | gwei |
|---|---|
| 0.01 | `10000000` |
| 0.1 | `100000000` |
| 0.5 | `500000000` |
| 1 | `1000000000` |

It is the most promised payment Prysm counts from that builder for one block: with a limit of 0.1 ETH, a bid of 0.01 ETH `value` plus 0.3 ETH `execution_payment` is valued at 0.11 ETH. Because the payment isn't guaranteed, it is also the most you can lose compared with your own block if the builder wins and doesn't pay. Prysm doesn't recommend an amount; read [Trusting builders](#trusting-builders-max_execution_payment) before choosing one.

### Configuring Gloas builders with flags

The flags set the same builder configuration for every key, the way `--suggested-fee-recipient` sets a default fee recipient. Per-key settings from a file, URL, or the keymanager API take priority over them.

| Flag | Effect |
|---|---|
| `--builder-urls` | Comma-separated builder URLs to request bids from, at most 64. Auth data agreed with a builder goes in a `0x`-hex fragment (`https://builder.example#0x0123`); otherwise the lowercased hostname is used. An invalid URL, a non-hex fragment, more than 64 entries, or a duplicate stops the validator client from starting. |
| `--builder-min-bid` | Minimum bid, in gwei: the bid value plus its execution payment, counted up to `--builder-max-execution-payment`. |
| `--builder-boost-factor` | Percentage applied to a bid's value before comparing it with your local payload: `100` is neutral, below `100` favors your payload, `0` always uses it (also against [P2P bids](#how-a-bid-is-valued)). |
| `--builder-max-execution-payment` | Maximum execution payment, in gwei, counted toward a bid. `0` counts only the value backed by the builder's stake; anything above counts payment the builder only promises. See [Trusting builders](#trusting-builders-max_execution_payment). |

Set `--builder-max-execution-payment` with `--builder-urls`; on its own, `--builder-urls` counts none of a builder's promised payment. Pass the flags on every start: they apply only to the run that sets them, and Prysm warns when it drops stored values because the flags are missing. Before the fork, a non-empty `--builder-urls` also registers keys with MEV-Boost, as `--enable-builder` does, including keys whose `builder` object has only v1 fields; set `"builders": []` on a key to keep it out.

## How proposer settings are supplied

- **Command-line flags**, which set `default_config` for every key: `--suggested-fee-recipient`, `--suggested-gas-limit`, and the [builder flags](#configuring-gloas-builders-with-flags).
- `--proposer-settings-file=<path>`: a local JSON or YAML file using the schema on this page.
- `--proposer-settings-url=<url>`: a URL that returns the same schema as JSON (Prysm sends a GET request; YAML is only supported for files).
- [Keymanager APIs](/apis/keymanager-api.mdx): endpoints for each key's fee recipient, gas limit, graffiti, and builder configuration.

`--proposer-settings-file` and `--proposer-settings-url` can't be combined; the validator client won't start with both. Files and URL responses are parsed strictly: a field name Prysm doesn't recognize, a `version` above `2`, or a `builder_pubkeys` or `auth_data` value that isn't `0x`-hex stops the settings from loading. (`pubkeys`, the old name of `builder_pubkeys`, is the common case.)

A `default_config` in a file or URL replaces the defaults set by flags, including `--suggested-fee-recipient` and `--suggested-gas-limit`, so put those values in the file. With a v1 file, `--suggested-gas-limit` also overwrites the `gas_limit` inside `builder` for every key, as it always has.

Loaded settings are saved in the validator client database, so changes made through the keymanager APIs survive restarts. A file or URL takes priority over the database at startup: a non-empty `proposer_config` replaces all stored per-key settings, and a `default_config` replaces the stored default. If you manage keys through the keymanager APIs and restart with a settings file, those keys are reset to what the file says.

The configured key considers bids from two builders, counting up to 0.1 ETH of builder A's promised execution payment and none of builder B's, and ignores bids worth less than 0.01 ETH. Every other key uses the default, which requests no builder bids because `builders` is an empty list.

Amounts and gas limits can be written as strings (`"60000000"`) or plain numbers; strings are recommended because the keymanager API uses them. `version` must be a plain number. All amounts (`min_bid`, `max_execution_payment`) are in gwei.

### Top-level fields

| Field | Description |
|---|---|
| `version` | **Optional.** `2` is the current schema. A file with no `version` is treated as version 2 as soon as it contains any v2 builder field (`builders`, `min_bid`, `builder_boost_factor`, or `max_execution_payment`), with an info log. Don't set `version: 1` on a file with v2 builder fields; Prysm takes the version as written. A `version` above `2` fails to load. |
| `proposer_config` | A map from validator BLS public key (98-character `0x`-prefixed hex) to the options for that key. |
| `default_config` | Options for every validator key not listed in `proposer_config`. |

### Options (per key, and in `default_config`)

| Field | Description |
|---|---|
| `fee_recipient` | The Ethereum address that receives priority fees and, after Gloas, builder payments. A per-key value overrides `default_config`, which overrides `--suggested-fee-recipient`. |
| `gas_limit` | The gas limit your validator asks for in blocks built for it. **New in v2 at this level.** Leave it unset to follow the network's [scheduled gas limit](#the-gas-limit-schedule), or the chain default in your Prysm release when no schedule entry applies (the [command-line options](/configure-prysm/command-line-options.mdx) page shows that default for `--suggested-gas-limit`). Set it only to use a fixed value instead; see the warning below. In v1, the gas limit was set inside `builder`; that location stops working at the Gloas fork. |
| `graffiti` | The graffiti string included in blocks proposed by this key. |
| `builder` | Builder configuration for this key. See below. Leave it out to use the builder configuration from `default_config`. |

:::warning A gas limit you set overrides the gas limit schedule

From the Gloas fork onward, a `gas_limit` set here, or passed with `--suggested-gas-limit`, is the gas limit your validator signs into its proposer preferences. It overrides the network's [scheduled gas limit](#the-gas-limit-schedule), so the key keeps that value and doesn't pick up scheduled increases. Prysm warns at startup when the flag is set, and once per epoch when it signs a preference that differs from the schedule. Unless you want a fixed gas limit, leave `gas_limit` unset and don't use the flag.

:::

### The `builder` object

| Field | Description |
|---|---|
| `builders` | The builders this key requests bids from. See [Builder entries](#builder-entries). Leaving it out means the key uses the list from `default_config`; an empty list (`[]`) means it requests bids from no builders (bids broadcast over P2P can still win; see [How a bid is valued](#how-a-bid-is-valued)). At most 64 entries. Duplicate or invalid entries are dropped with a warning; values that aren't valid `0x`-hex fail the load. |
| `min_bid` | Minimum [effective value](#how-a-bid-is-valued), in gwei; lower bids are ignored. Unset means no minimum. Can be overridden per entry. |
| `max_execution_payment` | Maximum execution payment, in gwei, counted toward a bid. **This is how much you trust the builder to pay; read [Trusting builders](#trusting-builders-max_execution_payment) first.** Unset or `0` counts none. Can be overridden per entry. |
| `builder_boost_factor` | Percentage applied to bid values before comparing them with your local block: `100` (default) is neutral, above favors builders, below favors your block, `0` means a bid never wins. Can be overridden per entry. |
| `enabled` | **Legacy (v1).** Registers the key with MEV-Boost before the Gloas fork, even next to `builders: []`. Ignored by the Gloas builder settings and removed at the fork. In v2, a non-empty `builders` list registers the key instead; see [Running v2 settings before the Gloas fork](#running-v2-settings-before-the-gloas-fork). |
| `gas_limit` | **Legacy (v1).** The MEV-Boost registration gas limit. In v2, set `gas_limit` next to `fee_recipient` instead. |

The v1 `relays` field is deprecated and ignored, but still accepted.

### Builder entries

Each entry in a `builders` list describes one builder your validator can request bids from:

| Field | Description |
|---|---|
| `url` | **Required.** The builder's HTTP(S) endpoint, up to 2048 bytes, with an ASCII hostname. Entries with the same `url` and `auth_data` are duplicates. |
| `min_bid` | Overrides the enclosing config's `min_bid` for this builder. |
| `max_execution_payment` | Overrides the enclosing config's `max_execution_payment` for this builder. Set it here rather than for the whole config. |
| `builder_boost_factor` | Overrides the enclosing config's `builder_boost_factor` for this builder. |
| `builder_pubkeys` | Optional allowlist of builder BLS public keys (48-byte `0x`-hex strings, at most 64). If set, only bids from these builders are accepted from this URL. |
| `auth_data` | Optional bytes, as a `0x`-hex string, that your validator signs to authenticate its requests to this builder. Defaults to the lowercased hostname of `url` (`builder.example`; IPv6 in brackets), as the [builder spec](https://github.com/ethereum/builder-specs/blob/main/specs/gloas/validator.md#default-auth-data) defines, so most operators never set it. At most 4096 bytes. |

A field not set on an entry is taken from the enclosing `builder` config, and then from the `builder` config in `default_config`. `builder_pubkeys` and `auth_data` use the same names and `0x`-hex format as the [keymanager builder API](#keymanager-apis), so you can copy an entry between the two. Files written for an earlier development build used a `pubkeys` field with base64 values; rename the field and convert each value to hex (`echo '<base64 value>' | base64 -d | od -An -tx1 | tr -d ' \n'`, then prefix `0x`).

## How a bid is valued

`min_bid`, `max_execution_payment`, and `builder_boost_factor` all affect how Prysm chooses a payload after Gloas. When your validator is about to propose, the beacon node builds a local payload, requests bids from your configured builders, collects bids broadcast over the P2P network, and then:

1. **Checks that each bid is valid**, the same way the chain does: the builder is active and can pay the bid's `value`, the bid is for your slot, parent block, fee recipient, and gas limit preference, and the signature verifies. Bids from blacklisted builders are skipped.
2. **Calculates each bid's effective value**: `value`, which the protocol guarantees from the builder's staked balance, plus `execution_payment`, which the builder only promises to pay inside the payload, **counted up to your `max_execution_payment`**. With that unset or `0`, only `value` counts.
3. **Discards bids below the minimum.** A bid whose effective value is below the applicable `min_bid` is discarded.
4. **Compares bids.** Each remaining bid's effective value is multiplied by its `builder_boost_factor` divided by 100 and compared with your local payload and the other bids. The highest wins; ties go to the local payload.

Builders are queried in parallel with a `600ms` budget by default (`--builder-bid-timeout` on the beacon node); a builder that doesn't answer in time is skipped for that proposal, not blacklisted.

**Bids from the P2P network.** Builders can also broadcast bids to every proposer over P2P, without being configured anywhere. These must carry a zero `execution_payment`, so only their guaranteed `value` counts, and Prysm compares them with your local payload on every proposal, whether or not you configured any builders, using the `min_bid` and `builder_boost_factor` from your builder config (none and `100` if you have no config). An empty `builders` list stops bid requests, not P2P bids; to always use your own block, set `builder_boost_factor` to `0`.

If no bid wins, your block commits to a self-build bid, and your validator client signs and publishes the execution payload envelope from your local execution client right after the block. You still need a synced execution client: if it can't produce a payload, Prysm falls back to the best P2P bid, and if there is none, the proposal fails.

**Builders that don't deliver.** A builder that wins and then doesn't reveal its payload is blacklisted for the rest of the epoch, or for 256 epochs (about 27 hours) after a second failure within five epochs. Its bids are ignored and not forwarded to peers; revealing a valid payload clears the record. If seven or more builders are blacklisted at once, the beacon node uses only its own block until they recover.

## Trusting builders: `max_execution_payment`

:::caution Setting this means trusting a builder to pay

A bid's `value` is guaranteed: the protocol checks that the builder's staked balance covers it before the bid can win, and pays your fee recipient from that balance once the payload is revealed. A bid's `execution_payment` is only a promise to pay your fee recipient inside the payload. The protocol doesn't hold that amount or check that it is paid.

Setting `max_execution_payment` above `0` lets a bid win on promised payment, so a malicious or faulty builder can outbid everyone and never pay. Set it to the most you are willing to risk on that builder in a single block, and set it on the entries of builders you trust rather than for the whole config. Leaving it unset or `0` risks nothing, but builders whose bids depend on execution payments will rarely or never be used; Prysm warns at startup about entries that leave it unset. The maximum, `18446744073709551615` (2^64 − 1), accepts any promised amount and isn't recommended.

Unlike some other clients, Prysm has no separate flag that gates this. A non-zero `max_execution_payment` is all it takes.

:::

## The gas limit schedule

From the Gloas fork onward, your validator signs a gas limit preference, and builder bids must be compatible with it. [EIP-8261](https://eips.ethereum.org/EIPS/eip-8261) defines a gas limit schedule in the network configuration that clients use as the default for that preference, so raising the network's gas limit no longer needs every operator to change a flag.

- **What it is.** `GAS_LIMIT_SCHEDULE` entries in the network config, each with an `EPOCH` and a `GAS_LIMIT`. The most recent entry whose epoch has been reached applies, from the Gloas fork epoch onward. For a key without a gas limit you set, Prysm signs the scheduled value, or the chain default in your release if no entry applies yet. The schedule is a recommendation: a block's gas limit can still move by at most about 1/1024 of the parent's per block, so increases take effect over many blocks, and a builder bid must use exactly the gas limit that moves from the parent's toward your preference within that step.
- **Overriding it.** A `gas_limit` you set, or `--suggested-gas-limit`, overrides the schedule; Prysm uses your value and warns once per epoch when it signs a preference that differs from the scheduled one.
- **Where it comes from.** The validator client reads the schedule from its own network config, not from the beacon node. For the networks Prysm supports, it is built into each release. On a custom network or devnet, pass the network's `config.yaml` to the validator client with `--chain-config-file` too, or it won't have the schedule.

To see the gas limit a key is signing, call the keymanager `GET /eth/v1/validator/{pubkey}/gas_limit` endpoint.

## Inheritance and merge rules

`min_bid`, `max_execution_payment`, and `builder_boost_factor` are inherited one field at a time. A per-key value takes priority. If the key doesn't set a field, the value from `default_config` is used. If neither sets it, the default applies: no minimum bid, no promised payment counted, and a boost factor of 100. Builder entries inherit from their enclosing config in the same way.

The `builders` list is **replaced, not merged**. A per-key list, including an empty list (`[]`), replaces the default list completely. If a key doesn't set `builders`, it uses the default list. So to stop a single key from requesting builder bids, set `"builders": []`.

`gas_limit` works the same way: a per-key value takes priority over `default_config`. If neither sets it, the network's scheduled gas limit or the chain default applies.

## Running v2 settings before the Gloas fork

Between upgrading Prysm and the fork epoch, your validator still uses MEV-Boost, and your v2 settings decide which keys to register:

| Your v2 settings | Before the fork (MEV-Boost) | After the fork (Gloas) |
|---|---|---|
| Non-empty `builders` list | Key is registered with MEV-Boost relays, as with v1 `enabled: true` | Bids are requested from the listed builders |
| Empty list (`builders: []`) | Key is **not** registered, unless the legacy `enabled: true` is also set | No builder bids are requested |
| No `builders` field, but other builder fields set (`min_bid`, etc.) | The key's own config doesn't decide; the `default_config` setting applies, if any | Uses the `builders` list from `default_config` |
| Legacy `enabled: true` together with v2 fields | Key is registered | `enabled` is ignored, and removed at the fork |

Registration still uses your fee recipient and gas limit (a `gas_limit` next to `fee_recipient` wins over a legacy one inside `builder`), and the beacon node's `--http-mev-relay` setup doesn't change until the fork. The keymanager `builder_config` endpoints return `501` until your network schedules the fork.

## Migrating from v1 to v2

Prysm doesn't convert v1 builder settings automatically. The v1 fields control MEV-Boost registration, which doesn't exist after the fork.

### What replaces what

| To set | v1 | v2 |
|---|---|---|
| The file's schema version | no `version` field, or `version: 1` | `version: 2`. Optional: a file with no `version` is treated as v2 once it has any v2 builder field below. If the file says `version: 1`, change it to `2` |
| Use builders for a key | `builder.enabled: true` | a non-empty `builder.builders` list |
| Don't request builder bids for a key | `builder.enabled: false` | `builder.builders: []`, or no `builder` object to use the default |
| Which builders to use | not possible: `--http-mev-relay` set one relay for every key | `builders[].url`, per key |
| Accept bids only from specific builders | not possible | `builders[].builder_pubkeys` |
| Authenticate your requests to a builder | not possible | `builders[].auth_data` (defaults to the URL's hostname) |
| A gas limit | `builder.gas_limit`, or `--suggested-gas-limit` | `gas_limit` next to `fee_recipient`, or `--suggested-gas-limit`; both override the [gas limit schedule](#the-gas-limit-schedule) from the fork onward, so leave them out to follow it |
| Ignore bids below a minimum | beacon node `--min-builder-bid`, for every key | `min_bid`, per builder config or per entry |
| Favor your local block over builder bids | beacon node `--local-block-value-boost`, for every key | `builder_boost_factor`, per builder config or per entry |
| Count a builder's promised execution payment | not possible: you relied on the relay | `max_execution_payment`, per builder config or per entry; unset counts none |
| Relays | `relays` | deprecated and ignored, because Gloas has no relays |
| A fee recipient or graffiti | `fee_recipient`, `graffiti` | unchanged |

The v2 example keeps `gas_limit` so that the two files match; you probably want to delete it instead (step 2).

To migrate:

1. Replace each `"enabled": true` with a `builders` list and set `max_execution_payment` on each entry. Replace each `"enabled": false` with `"builders": []`, or remove the `builder` object so the key uses the default.
2. **Delete `gas_limit` instead of moving it**, unless you want a fixed gas limit. Next to `fee_recipient`, it overrides the [gas limit schedule](#the-gas-limit-schedule) from the fork onward; inside `builder` it never did.
3. Delete `relays` if present. Optionally add `"version": 2`; the builder fields already make the file v2.
4. Restart the validator client and check the [startup logs](#startup-warnings-explained).

### What happens if you don't migrate

Nothing changes before the fork, except that Prysm warns at startup about deprecated v1 builder fields once your network schedules Gloas. At the fork epoch, Prysm removes `enabled` and the `gas_limit` inside `builder` with a warning and keeps fee recipients and graffiti. Your gas limit follows the network schedule, and Prysm requests no builder bids until you add v2 settings (trustless P2P bids can still beat your own block; see [How a bid is valued](#how-a-bid-is-valued)). Nothing in this fallback counts a payment that isn't backed by a builder's staked balance.

## Flag changes and deprecations

| Flag | Status |
|---|---|
| `--suggested-fee-recipient` (validator) | Unchanged. |
| `--proposer-settings-file` / `--proposer-settings-url` (validator) | Unchanged. You still can't use both. |
| `--enable-builder` / `--enable-validator-registration` (validator) | **Legacy.** Registers all keys with MEV-Boost before the fork and does nothing after it; Prysm warns when it is used with v2 settings. Per-key v2 settings win over it, but keys that use `default_config` are registered even if `default_config` has `"builders": []`. Replaced by a `builders` list, `--builder-urls`, or the keymanager API. |
| `--builder-urls`, `--builder-min-bid`, `--builder-boost-factor`, `--builder-max-execution-payment` (validator) | New. Set the default Gloas builder configuration for every key without a settings file. See [Configuring Gloas builders with flags](#configuring-gloas-builders-with-flags). |
| `--suggested-gas-limit` (validator) | Sets the default gas limit before the fork (registered with builders) and after it (signed into proposer preferences, overriding the [gas limit schedule](#the-gas-limit-schedule), with a startup warning on Gloas-scheduled networks). Remove it to follow the schedule. Applies only to the run that sets it. A `default_config` in a settings file or URL replaces it, so set `gas_limit` in the file instead; with a v1 file, it also overwrites the `gas_limit` inside `builder` for every key until the fork. |
| `--stateless` (validator) | New with Gloas. The validator requests the block and execution payload envelope together and republishes the envelope itself. Forced on when several beacon nodes are configured on a network with Gloas scheduled. |
| `--http-mev-relay` (beacon node) | MEV-Boost only, which ends at the fork. Afterwards the beacon node contacts the builders your validator client lists; no beacon node builder flag is needed. |
| `--builder-bid-timeout` (beacon node) | New, optional. How long the beacon node waits for builder bids before using P2P bids or the local payload. Default `600ms`; Gloas only. |
| `--min-builder-bid`, `--local-block-value-boost` (beacon node) | MEV-Boost settings used before the fork. After the fork, use `min_bid` and `builder_boost_factor` in v2 proposer settings. |
| `--with-builder` (prysmctl validator) | **Legacy.** Generates MEV-Boost builder settings for use before the fork, and logs a warning. |

## Keymanager APIs

The existing proposer keymanager endpoints still work, with two changes in behavior and a new group of builder endpoints. See [Keymanager APIs](/apis/keymanager-api.mdx) for authentication.

- **Gas limit endpoints** read and write the `gas_limit` next to `fee_recipient` and no longer require a builder to be enabled. From the fork, `GET` returns the gas limit the key signs: its own or `default_config`'s value if set, otherwise the scheduled gas limit or the chain default. Before the fork it returns the MEV-Boost registration value. `DELETE` resets the key to `default_config`'s gas limit if one is set (from the file or `--suggested-gas-limit`), otherwise removes the key's value so it follows the schedule; it returns `404` if there is nothing to reset.
- **Fee recipient, gas limit, and graffiti writes** no longer copy the builder settings from `default_config` onto the key.
- **`GET`/`POST`/`DELETE /eth/v1/validator/{pubkey}/builder_config`** (new, from [keymanager-APIs #88](https://github.com/ethereum/keymanager-APIs/pull/88)) manage a key's builder config. `GET` returns the key's config combined with `default_config`, with a value for every field (`"0"` for no minimum, `"100"` for the default boost, `"0"` for no counted payment); sending it back unchanged pins those values on the key. `POST` replaces the whole config and leaves fee recipient, gas limit, and graffiti alone; an empty object removes the key's builder config, and unknown fields are ignored. `DELETE` removes the key's builder config so it uses `default_config` again. Integers are decimal strings and byte fields (`builder_pubkeys`, `auth_data`) are `0x`-hex; `max_execution_payment` exists only per builder entry, so `GET` copies a config-level value onto each entry and `POST` can't set one. The endpoints return `501` on networks with no Gloas fork scheduled.

## Startup warnings explained

Unknown fields, a `version` above `2`, invalid builder flags, and `builder_pubkeys` or `auth_data` values that aren't `0x`-hex stop the settings from loading. Builder entries that break a size or format limit are dropped with a warning instead. Most messages below appear at startup; a few repeat while their cause remains.

| Log message (abbreviated) | Meaning | Action |
|---|---|---|
| "Proposer settings contain v2 builder fields but no version; treating the source as version 2" (info) | Your unversioned settings are being read as version 2. | None. Add `"version": 2` to avoid the message. |
| "Proposer settings contain deprecated v1 builder fields (enabled, builder-level gas limits); they stop applying at the gloas fork…" | Your network has Gloas scheduled and your settings contain v1 builder fields (`--enable-builder`, or `--suggested-gas-limit` without v2 settings, counts too). | Migrate to v2 before the fork epoch. |
| "Proposer settings contain v1 builder fields, which do not apply to gloas; proposer preferences are prepared with defaults…" | Logged at each epoch start from the last epoch before the fork while v1 builder fields remain. | Migrate to v2 now. |
| "V1 builder settings, including gas limits, do not apply to gloas and were replaced with defaults…" | At the fork, Prysm removed your v1 builder settings. | Add v2 settings if you want builders or a fixed gas limit. |
| "Builders have no max_execution_payment (default 0): execution payment is ignored, so these builders' bids may lose to the local payload." | The listed builders have no `max_execution_payment` on the entry or on any `builder` config they inherit from, so only each bid's `value` counts. Gloas-scheduled networks only; an explicit `0` doesn't trigger it. | Set `max_execution_payment` on each entry after reading [Trusting builders](#trusting-builders-max_execution_payment), or ignore it if that's what you want. |
| "Removed N invalid or duplicate builder entries from proposer settings" | Entries had a missing, too long, or unparseable `url`, a non-ASCII hostname, more than 64 entries (the first 64 are kept), more than 64 or wrong-length `builder_pubkeys`, `auth_data` over 4096 bytes, or duplicated another entry. | Fix the entries named in the log's `reasons` field (duplicates are counted but not listed). |
| "--enable-builder is legacy (pre-gloas) mev-boost content and has no effect after the gloas fork…" | `--enable-builder` is set together with v2 settings. | Remove the flag once your v2 settings say which keys use builders. |
| "--suggested-gas-limit overrides the network gas limit schedule from the Gloas fork; remove it to follow the schedule" | The flag fixes your gas limit, so scheduled increases won't apply. A second warning follows if the value is above the highest scheduled limit. | Remove the flag unless you want a fixed gas limit. |
| "Dropped the default builder settings a previous run stored in the validator DB…" (or the same for the default gas limit) | Stored default builders or a default gas limit weren't reused because this run's flags and settings source don't set them. | Pass the flags (or the settings source) on every start. |
| "…configure Gloas builders, but this network has no Gloas fork scheduled" | Builder flags are set on a network without Gloas. Only `--builder-urls` does anything here (it enables MEV-Boost registration). | Remove the flags, or check that you're on the right network. |
| "The default_config from --proposer-settings-file replaces the builder defaults set by …" | The settings source and the builder flags both set defaults; the file wins. | Expected. Remove the flags, or remove `default_config` from the source. |
| "Default builder config has no default fee recipient; only keys with their own fee recipient can register" | `default_config` has a `builder` object but no fee recipient, so keys without their own fee recipient aren't registered with MEV-Boost. Repeats every slot before the fork. | Set `fee_recipient` in `default_config`, or use `--suggested-fee-recipient` if you have no settings source. |
| "Per-key proposer settings saved in the validator DB by a previous run differ from the configured settings file/URL…" | Your settings source is replacing stored per-key settings; the log lists them in `droppedKeys` and `overriddenKeys`. | Expected if you manage keys with a file. Keymanager API changes don't survive a restart while a file or URL is configured. |

## Frequently asked questions

#### Do I have to do anything if I never use builders?

Set your fee recipient, with a flag or in a file. You don't need `"version": 2`, a `builder` section, or any new flags. After the fork, your validator requests no builder bids and its gas limit follows the network schedule, unless you set `--suggested-gas-limit` or a `gas_limit`. Trustless bids that builders broadcast over P2P can still beat your own block on guaranteed value (see [How a bid is valued](#how-a-bid-is-valued)); if you never want that, set `builder_boost_factor` to `0` in `default_config` or pass `--builder-boost-factor=0`.

#### Which networks does this apply to right now?

Bids are only requested and compared on networks with a Gloas fork epoch scheduled: testnets and devnets first, and mainnet once the fork is scheduled there. On other networks, a v2 file loads without errors, the keymanager builder endpoints return `501`, and the Gloas-specific warnings aren't logged. A non-empty `builders` list still registers the key with MEV-Boost on any network, and an empty list still opts it out.

#### Can I mix the flags and a v2 file?

Yes, and the file takes priority: a `default_config` in the file replaces all flag defaults, so put your fee recipient and any gas limit in the file rather than in `--suggested-fee-recipient` or `--suggested-gas-limit`. `--enable-builder` only affects registration before the fork; `--suggested-gas-limit` keeps applying after it and overrides the schedule. Prysm warns about both.
